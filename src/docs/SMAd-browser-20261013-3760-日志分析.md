# browser-20261013-3760.log 分析

## 结论

该日志中的主要异常关闭由 SMAd 自己触发：DeviceTargetController 接收到超过 4 MiB 的单条 CDP 消息后抛出 IOException，故障回调将其标为 StartupFailed 并取消整次执行，随后正常资源回收链路强制结束浏览器。

120 次这种停止请求发生时，浏览器进程均仍存活。日志没有记录回收开始前的进程退出，也没有 page.crashed 或 connection.disconnected 事件。因此，这批记录支持“接收器报错后程序主动关闭”的结论，没有证明 Chromium 原生闪退。

## 对应代码与后续修改方向

`Plugins/SMAd/DeviceEmulation/DeviceTargetController.cs` 的 ReadAsync 累积 WebSocket 分片，单条消息大于 `4 * 1024 * 1024` 字节即抛异常。catch 调用 ReportFailure；`SMAdTask.ConfigureContextAsync` 的回调调用 RequestStop(StartupFailed) 并取消执行。这个链路解释了日志中的取消和主动关闭顺序。

DeviceTargetController 还额外发送 Page.enable，但它的事件接收逻辑仅使用 Target.attachedToTarget 和 Target.detachedFromTarget，不使用收到的 Page 事件。业务页面自身另有 Page.enable。优先检查并移除设备控制连接上不需要的 Page 订阅，再完善大消息处理：无关事件不应仅因超过本地接收阈值就取消整次健康执行，真正连接断开或关键协议数据不可用仍应保留明确错误。

现有日志没有记录超限消息的 method/id 或实际总长度，尚不能确定具体是哪类消息、哪个 iframe 或页面触发；不要直接断言是特定站点内容。修复时应补充消息类型、长度等元信息，不记录消息正文，并用超过 4 MiB 的 WebSocket 分片夹具验证接收后续响应和故障隔离。不能仅通过增大阈值掩盖问题。

同时应将运行期间的设备控制故障与首次初始化失败分开记录，避免所有故障均显示 StartupFailed；正常完成时也应区分历史 RequestFailed 诊断与本次真正的关闭原因，减少误读。
